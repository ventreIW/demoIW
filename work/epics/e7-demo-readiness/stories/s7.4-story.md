# Story: End-to-end demo flow validation — the full path, proven, under 10 minutes

**Branch:** `story/s7.4/e2e-demo-flow-validation` · **Backlog:** B-16 · **NFR:** NFR-01

## User Story
As the person presenting demoIW,
I want an automated test that drives the entire demo path end to end and fails loudly when any
step breaks,
so that I can walk into the demo knowing the path works, rather than discovering a broken step
in front of an audience.

## Acceptance Criteria

### Scenario: The complete demo path runs unattended and succeeds
```gherkin
Given a clean database
When the smoke test drives the full path — generate a scenario, activate it, score and persist,
     read the prioritized queue, open a case, record a contact result, generate a communication
     draft, read the executive KPIs, and ask a natural-language question
Then every step returns a success status and a well-formed payload
And the whole path completes in under 10 minutes (NFR-01)
```

### Scenario: A broken step fails the test rather than being skipped
```gherkin
Given any single step of the demo path returns an error or an empty result
When the smoke test runs
Then the test fails and names the step that broke
And it does not pass by iterating over an empty collection (the BUG-02 shape)
```

### Scenario: The demo is repeatable
```gherkin
Given the smoke test is run twice with the same seed
When the two portfolios are compared
Then the scores and category distribution are identical (BUG-05, ADR-011)
```

### Scenario: The path is exercised against the real database driver
```gherkin
Given a PostgreSQL instance and the Alembic migrations applied from zero
When the same smoke test runs against it
Then it passes — proving asyncpg and the Postgres-specific migrations, including 0004,
     are exercised rather than assumed (E6 M4)
```

## Examples (Specification by Example)

| Step | Call | Expected |
|---|---|---|
| Generate | `POST /scenarios/generate` seed 42, 100 clients, pinned `reference_date` | 201, `client_count == 100` |
| Activate | `PATCH /scenarios/{id}/activate` | 200, `status == "active"` |
| Score | `POST /scenarios/{id}/score` | 201, `scored_count > 0` |
| Queue | `GET /scenarios/{id}/prioritized` | 200, non-empty `cases`, `value_share >= threshold` |
| Filter | `GET /scenarios/{id}/prioritized?category=high` | 200, count equals the unfiltered high tally (BUG-02) |
| Case | `GET /scenarios/{id}/clients/{client_id}` | 200, invoices and payment history present |
| Contact | `POST` contact result | 201, triggers rescore |
| Comms | `POST` communication draft | 201, non-empty draft body, audit row written |
| KPIs | `GET /scenarios/{id}/kpis` | 200, `total_outstanding > 0`, `scored_at` present |
| NL query | `POST /scenarios/{id}/query` | 200, `answerable` true with chart + citation |
| Repeat | the whole path, twice, same seed | identical score multiset and category tally |

## Notes

- Runs last in E7 by design: it exercises everything the other three stories polished.
- Five defects fixed earlier today sit directly on this path (BUG-01 through BUG-05). This
  story is what would have caught them, which is the argument for it existing.
- **BUG-06 constrains the path.** A CSV-uploaded scenario cannot currently be scored, so CSV
  upload is exercised as far as it works (upload → persisted → listed) and the scored path
  uses a generated scenario. The limit is asserted explicitly rather than stepped around.
- The Postgres criterion is E6's M4 line item, open across five stories. It needs a running
  PostgreSQL; if unavailable the test must **skip loudly**, never pass silently.
