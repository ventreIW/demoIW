## Gate Policy

| When | Command | Scope |
|------|---------|-------|
| Per task | `rai gate check gate-tests --scope frontend/src/{dir}` | Tests for the changed modules only |
| Per task | `rai gate check gate-lint` | Full project (fast) |
| Per task | `rai gate check gate-format` | Full project (fast) |
| Per task | `rai gate check gate-types` | Full project (tsc --noEmit via frontend) |
| End of story | `rai gate check gate-tests --scope frontend/src` | Changed package only — not full suite |
| MR creation | `/rai-mr-create` | Full suite — the ONLY unscoped run |

NEVER run `npm test`/`npx vitest` directly — always `rai gate check gate-tests --scope <path>`.
If `rai gate check` fails/not found after one attempt, fall back to `cd frontend && npx vitest run <path> --no-coverage -w=false`.

## Execution Order
T1 → T2 → T3 → T4 (strictly sequential: tokens must land before layout/components; audit last, depends on all).
No circular dependencies. Risk-first: T1 (root cause, highest risk) first.

## Risks & Mitigations
- Token change could alter visual styles broadly → verify via Vitest + screenshot/visual smoke in T4; tokens reuse existing class names so scope is contained.
- axe-core in jsdom may miss real rendering contrast → T4 pairs automated jsdom scan with a manual keyboard pass + optional `@axe-core/cli` against a running server.
- WSL vitest is slow (60-180s) → always `--scope` to limit; use `--no-coverage` (memory).
- `rai gate check` may not run vitest for frontend → fallback documented above (one attempt then direct vitest).
