# Retrospective: S7.2 — Accessibility pass (WCAG 2.1 AA)

**Dates:** 2026-08-13 → 2026-08-13

## Summary

Accessibility pass that fixed 11 components in a single session. The root cause was more fundamental than expected: Tailwind tokens that the shadcn-style UI primitives depended on were entirely undefined (empty `theme.extend`), so primary buttons rendered with no background and focus rings were invisible. Defining the design tokens once in `globals.css` + wiring them in `tailwind.config.ts` restored the whole primitive set. This was the highest-leverage change in the story.

## What went well
- **Root-cause discovery during gemba walk**: The design phase correctly identified that undefined tokens caused invisible buttons + focus rings. This finding drove the architecture of the fix — one change set that fixed ~20 component instances instead of ~20 ad-hoc patches.
- **TDD for CSS infrastructure**: The config-level a11y-tokens test (T1) that parses globals.css + tailwind.config.ts effectively locks the token definition against regression. No way to accidentally revert the empty config.
- **axe-core integration**: The jsdom-based axe scan catches semantic WCAG violations (missing labels, broken landmarks, bad ARIA) in CI without a browser. The helper was simple to author (30 lines) and caught real issues during setup.
- **Skip-link + aria-current**: The semantic improvements (skip-link, nav landmark, main label, aria-current) are the highest-impact accessibility changes for keyboard users and screen reader usability.

## What to improve
- **Contrast verification in CI**: color-contrast can't run in jsdom (no canvas). For the demo deadline this is acceptable — a manual keyboard pass + real browser scan is sufficient. For ongoing work, a Playwright-based scan against the dev server would catch contrast regressions automatically.
- **Test speed on WSL**: 102s for 167 tests in jsdom is slow (WSL cross-filesystem). If development continues on the Windows side, moving the project to `/home/renor/` (native WSL FS) would eliminate the cross-filesystem overhead.

## Heutagogical Checkpoint
1. **What did I learn?** The tailwind.config `theme.extend.colors` with `hsl(var(--x) / <alpha-value>)` is the correct pattern for shadcn-style tokens to support opacity modifiers (`bg-primary/80`, `ring-ring/50`); the simple `'hsl(var(--x))'` form without `<alpha-value>` does not work for `hover:bg-primary/80` in Tailwind v3.4+.

2. **What would I change about the process?** The skill's verification gate policy (always use `rai gate check`) was designed for backend Python projects. For frontend vitest scopes, the fallback documented in the WSL pitfalls section (`cd frontend && npx vitest run <path> --no-coverage`) is the correct and only viable path — the pytest-based gate runner collects zero items from `frontend/` paths. The gate policy should detect `frontend/` prefix and route to vitest directly.

3. **Framework improvements?** The implement skill's git identity check (`bernardo-525` / `bernardojgm05@gmail.com`) is environment-specific and should be a project config, not hardcoded in the skill. Different developers (Renata vs Bernardo) use the same repo with different gitconfigs.

4. **What am I more capable of now?** Building repeatable component-level a11y scan tests with axe-core in jsdom; structuring a frontend-only accessibility fix around the root cause (tokens) rather than per-file patching; understanding Tailwind token resolution with CSS vars and `<alpha-value>`.
