# Story: Accessibility pass — WCAG 2.1 AA

## User Story
As a user with a keyboard-only workflow or low-vision need,
I want the app to meet WCAG 2.1 AA contrast and be fully keyboard-navigable,
so that every panel and control is usable without a mouse and legible enough to demo safely.

## Acceptance Criteria

### Scenario: Contrast meets AA for all text
```gherkin
Given the app renders any interactive page
When I audit foreground/background color contrast on all visible text and UI elements
Then every text element meets a 4.5:1 ratio (3:1 for large text and UI components)
```

### Scenario: All interactive elements keyboard-navigable
```gherkin
Given any panel with buttons, inputs, links, or controls
When I navigate using only the Tab / Shift+Tab / Enter / Space keys
Then every interactive element receives focus in a logical order and can be activated
```

### Scenario: Focus is always visible
```gherkin
Given a control receives keyboard focus
When I tab onto it
Then a clearly visible focus indicator is present and not clipped by overflow
```

### Scenario: Inputs have accessible labels
```gherkin
Given a form field or interactive control
When I inspect its accessible name
Then it has a programmatically-associated label visible to assistive technology
```

## Examples (Specification by Example)

| Input | Action | Expected Output |
|-------|--------|-----------------|
| Any page body text | axe-core scan | 0 color-contrast violations (AA) |
| Dashboard KPI cards (s6.2) | Tab through page | Focus reaches every control; order follows visual layout |
| Executive page question input (s6.4) | Tab + Enter | Input focusable and searchable, focus ring visible |
| Scenario/case tables | Tab through | Row actions reachable and activatable via keyboard |
| Any icon-only button | Check accessible name | Has aria-label / title; not exposed as unlabeled |
| Dialog / mobile nav | Escape key | Focus returns to the invoking control |
