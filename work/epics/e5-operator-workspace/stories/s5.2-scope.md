# s5.2 Scope — Case Detail View (+ Case-Aggregate Read API)

**Status:** Active — started 2026-07-28. Branch: `story/s5.2/case-detail-view`. Size: M.
Second story of E5; the hub that s5.3 and s5.4 depend on.

## In Scope

### Backend — Case-Aggregate Read API
- New endpoint `GET /api/v1/scenarios/{scenarioId}/clients/{clientId}`
- Returns a `CaseDetailResponse` composing:
  - Client profile (name, sector_description, payment_history_pattern)
  - Invoices list (folio, amount, issue_date, due_date, days_overdue, status) — ordered by due_date desc
  - Payments list (amount, payment_date, method) — ordered by payment_date desc
  - Communications list (draft_text, channel, tone, status, created_at) — ordered by created_at desc
  - Score (value, category, explanation) if one exists for this client
- Thin read model — no new persistence, uses existing repos:
  - `IClientRepository.get_by_id(client_id)`
  - `IInvoiceRepository` — query by client_id (may need new method `get_by_client_id`)
  - `IPaymentRepository` — query by linked invoices (may need `get_by_invoice_ids` or by client)
  - `IScoreRepository.get_by_scenario(scenario_id)` — then filter by client_id
  - Communication port `ICommunicationRepository` — new port + adapter
- **ContactResult** currently links to client_id + communication_id — may include latest contact result status
- 404 for unknown scenario or client

### Backend — New `ICommunicationRepository` port + SQLAlchemy adapter
- Port: `get_by_client_id(client_id) → list[Communication]`
- Adapter over existing `CommunicationORM` (from E2) + mapper
- Register in DI container

### Frontend — Case Detail Page
- New page at `[locale]/cases/[clientId]` (Next.js dynamic route)
- `lib/api/cases.ts` — `getCaseDetail(scenarioId, clientId)` fetch method
- Client profile section: name, sector, payment pattern
- Invoices table: sorted by due date, each row shows status, amount, overdue
- Payments table: sorted by payment date
- Communications log section: draft text (truncated), channel, tone, status, timestamp
- Loading state (skeleton/spinner) while API resolves
- Error state (friendly message, option to go back to case list)
- ES-first via next-intl; new message keys in both `es.json` and `en.json`
- Navigation: link from the s5.1 case list row to detail page

### Testing
- **Backend**: integration test for aggregate endpoint (200 + model shape, 404 cases)
- **Backend**: unit tests for `ICommunicationRepository` adapter (add + get_by_client_id)
- **Frontend**: component test for detail page (profile, invoices, payments sections render)
- **Frontend**: test loading and error states
- **Frontend**: contract test verifying response shape matches expectations

## Out of Scope

| Item | Reason |
|------|--------|
| Recording contact results / updating status | s5.3 |
| Communications generator (draft, edit, send) | s5.4 / s5.5 |
| Sorting/filtering on the detail page | Parking lot — read-only display |
| Paginating invoices/payments/comms lists | Demo scenarios produce manageable counts |
| Editing client data | Read-only view |
| Nested routing within the detail page | Single-level `[clientId]` page |
| Persisting locale preference to DB | Browser-only per b15 decision |
