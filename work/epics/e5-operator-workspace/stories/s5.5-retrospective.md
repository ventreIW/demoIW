# Retrospective: S5.5 — Communications Generator Frontend Flow

**Dates:** 2026-08-02 → 2026-08-02
**Estimated:** S (3-5 SP) | **Actual:** single session (~2h)

## Summary

Frontend flow for the communications generator: channel/tone selector, editable draft textarea, send with confirmation dialog. Included a minimal backend addition (PATCH send endpoint + repo `get_by_id`/`update` methods). All tasks completed in one session.

## What went well

- ContactResultForm pattern was an excellent template — the CommunicationsGenerator component followed it closely, reducing design surface
- T1 and T2 ran independently (backend + frontend foundation), allowing parallel work
- The `id` field gap in CommunicationSummaryResponse was caught during test writing, not in review
- Full test suite: 412 backend + 100 frontend all green

## What to improve

- The `id` field was missing from `CommunicationSummaryResponse`, requiring a contract change mid-story. Should have been flagged in the design phase
- The use case's ignored `repo.add()` return value caused a subtle bug where the API returned an unpersisted UUID — the frontend couldn't reference the communication for send. Caught by router tests but wasted a debug cycle
- The `CommunicationsGenerator` component tests needed `findByRole` instead of `getByRole` for async elements — a known testing pattern that should be documented

## Heutagogical Checkpoint

1. **What did I learn?** The `GenerateCommunicationDraft` use case silently returned an unpersisted ID because `repo.add()` generates a new UUID internally but the use case ignored the return value. Any use case that creates a domain object and passes it to `repo.add()` must return the persisted object, not the input.

2. **What would I change about the process?** Add a design checklist item: "Does the API response include all identifiers needed by downstream consumers?" The `id` field omission in `CommunicationSummaryResponse` was a design oversight that rippled through frontend API calls.

3. **Framework improvements?** The `rai-story-design` skill's Components table is good but should explicitly note: "For response models, verify that identifiers (id, key, ref) are included for any entity that the frontend needs to reference in subsequent API calls."

4. **More capable of now?** Better at identifying ID-propagation bugs from domain object creation through persistence to API response. Also more comfortable with Base UI Select's `onValueChange` signature (accepts `string | null`).

## Improvements applied

- Fixed `GenerateCommunicationDraft` to return `persisted` (repo.add return value)
- Added `id` to `CommunicationSummaryResponse` (both frontend type and backend model)
- Added `get_by_id` and `update` to `ICommunicationRepository` interface

## Patterns added / reinforced

- **Added** PAT-R-12: "Use cases must return persisted object from repo.add(), not the input object" — addresses the ID mismatch bug
- ContactResultForm pattern reinforced: reusable for form + API integration patterns
- `findByRole` vs `getByRole` for async elements in Vitest
