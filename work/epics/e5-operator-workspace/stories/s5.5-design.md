# S5.5 Design — Communications Generator Frontend Flow

## Problem

The operator can generate a draft via the s5.4 backend API, but there's no frontend UI to do so. The draft must be displayed, editable, and sendable from the case detail view — without leaving the page.

## Value

Completes the operator workflow from the epic brief: case list → detail → **generate draft → edit → send**. This is the final user-facing surface of the E5 workflow, unblocking the P-01 demo narrative.

## Complexity: Simple

- 2 main components (CommunicationsGenerator + CaseDetail integration)
- 1 external integration (backend API — POST /communications + PATCH /communications/{id}/send)
- Trivial logic (form state, API calls, text editing)
- Follows established ContactResultForm pattern

## Approach

### Frontend

Create a `CommunicationsGenerator` component (in `frontend/src/components/cases/`) following the ContactResultForm pattern:

- **Channel/Tone selector**: Two `<Select>` dropdowns for Channel enum (email, phone, whatsapp) and Tone enum (formal, firm, urgent)
- **Generate button**: Calls `POST /api/v1/scenarios/{sid}/clients/{cid}/communications` with selected channel+tone
- **Editable draft area**: `<textarea>` pre-filled with generated draft text, user can modify
- **Send button**: Shows a `window.confirm()` dialog, then calls `PATCH …/communications/{comm_id}/send` to transition draft → sent
- **States**: loading (spinner on generate/send), error (inline error box), success (toast/message after send)

Add API client functions to `frontend/src/lib/api/cases.ts`:
- `generateCommunication(scenarioId, clientId, { channel, tone })` — POST to generate endpoint
- `sendCommunication(scenarioId, clientId, commId)` — PATCH to send endpoint

Add `CommunicationRequest` and `CommunicationResponse` types to `frontend/src/types/case-detail.ts` (or a new `types/communication.ts`).

Integrate into `CaseDetail.tsx` as a new section below the communications log, gated by `scenarioId && clientId` (same pattern as ContactResultForm).

Add i18n keys as a `communications` section in `es.json`/`en.json` (parallel to `contactResult` structure).

### Backend (minimal addition)

The s5.4 backend has no send endpoint. Add a minimal endpoint:

1. Add `update` method to `ICommunicationRepository` (port)
2. Add `update` to `SQLAlchemyCommunicationRepository` (adapter)
3. Add a `PATCH /api/v1/scenarios/{scenario_id}/clients/{client_id}/communications/{comm_id}/send` route handler that:
   - Fetches the communication by ID
   - Validates it belongs to the scenario/client
   - Validates current status is `draft`
   - Updates status to `sent`
   - Returns the updated CommunicationSummaryResponse

This is a single router handler + 2 repo methods — no new use case needed (the route handles the simple status transition inline).

### Design decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | Use `window.confirm()` for send confirmation | No dialog component exists in the UI library. Simple `confirm()` avoids adding a new dependency. If UX requires styled modals, this can be upgraded later. |
| D2 | Send endpoint is a simple PATCH route handler | No business logic beyond status validation — a dedicated use case would be over-engineering. The route handler is 10 lines. |
| D3 | Follow ContactResultForm state pattern | Proven pattern: `useState` for form fields, loading/error/success, same error handling approach. Consistent UX. |
| D4 | Component is a separate file, not inlined in CaseDetail | Keeps CaseDetail.tsx manageable; CommunicationsGenerator is a self-contained form with its own state and tests. |

### Legacy sweep

Nothing — this is net-new frontend code. The backend send endpoint is a gap-fill, not a replacement.

### Drift risks

No drift risk identified. The change is isolated to one component and its integration point. No coupling edges across >3 modules.

## Examples

### API client usage

```typescript
// Generate draft
const draft = await generateCommunication(scenarioId, clientId, {
  channel: 'email',
  tone: 'formal',
})
// draft: { channel: 'email', tone: 'formal', draft_text: '...', status: 'draft', created_at: '...' }

// Send draft (after confirmation)
const result = await sendCommunication(scenarioId, clientId, draftId)
// result: { channel: 'email', tone: 'formal', draft_text: '...', status: 'sent', created_at: '...' }
```

### Backend PATCH contract

```
PATCH /api/v1/scenarios/{sid}/clients/{cid}/communications/{commId}/send

Request: (empty body)
Response 200: CommunicationSummaryResponse with status: "sent"
Response 404: { detail: "Communication not found" }
Response 409: { detail: "Communication is not in draft status" }
```

### Component state machine

```
IDLE → GENERATING (loading) → DRAFT_READY (editable textarea)
DRAFT_READY → EDITING (user modifies text)
DRAFT_READY → CONFIRMING (window.confirm shown)
CONFIRMING → SENDING (loading) → SENT (success message)
CONFIRMING → DRAFT_READY (user cancelled)
Any state → ERROR (inline error box, retry available)
```

## Acceptance Criteria

### MUST
- [ ] Channel/tone selector renders with all 3 channels and 3 tones
- [ ] "Generate" button calls POST /communications and displays draft in editable textarea
- [ ] Draft textarea is editable; modifications persist in local state
- [ ] "Send" button shows confirmation dialog
- [ ] Confirming send calls PATCH /communications/{id}/send and transitions to "sent"
- [ ] Cancelling send leaves draft unchanged
- [ ] Backend send endpoint returns 200 on valid draft, 409 on already-sent
- [ ] API errors (generate/send) show inline error messages with retry
- [ ] Loading states shown during generate/send API calls
- [ ] All Vitest tests pass; typecheck + lint + format clean
- [ ] i18n keys added for both es/en (all labels, options, status messages)

### SHOULD
- [ ] Component reset after successful send (ready for next draft)
- [ ] Backend 404 for missing scenario/client returns clear error

### MUST NOT
- [ ] No real message delivery (email/SMS/WhatsApp) — send = status transition only
