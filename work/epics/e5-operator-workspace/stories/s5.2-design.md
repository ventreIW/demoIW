# s5.2 Design — Case Detail View (+ Case-Aggregate Read API)

**Story:** s5.2 | **Complexity:** Moderate | **Status:** Draft
**Branch:** `story/s5.2/case-detail-view`

## Problem

The operations panel (s5.1) shows a prioritized list of cases, but clicking a row does nothing. The operator has no way to see a client's full picture — profile, invoices, payment history, communications log, and score — without switching to a different tool or inspecting raw data.

## Value

The operator can assess an account at a glance from a single detail view, enabling informed decisions about contact priority and approach for each case. Unblocks s5.3 (contact result) and s5.4 (comms generator), which both launch from the case detail.

## Approach

New backend case-aggregate read endpoint that composes over five existing repositories (Client, Invoice, Payment, Score, Communication) — no new persistence or use case layer. New `ICommunicationRepository` port + SQLAlchemy adapter. New frontend dynamic route `[locale]/cases/[clientId]` following the s5.1 page pattern (async server component, `MainLayout`, next-intl). Add `get_by_client_id` to `IInvoiceRepository`/`IPaymentRepository` ports + adapters.

### Key Design Decisions

| ID | Decision | Rationale |
|----|----------|-----------|
| D1 | Thin read model, no use case layer | The aggregate endpoint is a read-only composition over existing repos. A use case would be a pass-through. The router calls repos directly, same pattern as the existing scenarios router. |
| D2 | Payment query by client_id (not invoice_ids) | Add `get_by_client_id` to `IPaymentRepository` that joins through `InvoiceORM → ClientORM` — same join pattern as `get_by_scenario_id` but filtered to a single client. |
| D3 | Score filtered client-side from scenario scores | `IScoreRepository.get_by_scenario` already returns all scores. Filtering by client_id in-memory is O(n) ≤ 500 clients — negligible overhead, avoids adding a new port method. |
| D4 | Dynamic route `[locale]/cases/[clientId]` | Matches the Next.js `[locale]` layout pattern. clientId is a path parameter, fetched server-side via the new endpoint. Follows s5.1 page pattern. |
| D5 | CaseTable modified for navigation link | Add a Link wrapper to each client name cell, pointing to `/{locale}/cases/{clientId}`. Minimal change to existing code. |

### Lean Design Gates

- **KISS**: Router calls repos directly — no new use case layer. Thinest possible read model.
- **DRY**: Reuses existing `get_by_scenario_id` patterns. No new ORM models or mappers — `CommunicationORM` and converters already exist.
- **YAGNI**: No pagination (demo data), no editing (read-only), no filtering/sorting on detail. The MVP is a read-only aggregate.
- **MVP**: Profile section + invoices table + payments table + comms log + score. That's the minimum to unblock s5.3 and s5.4.

**Nothing — this is net-new.** No V1 is being replaced.

`governance/drift-hotspots.json` not found — no drift catalog. AG4 assessment: the change touches ~6 backend files (router, port × 3, adapter, container) and ~5 frontend files. This is reasonable for an M-sized story with one new endpoint + one new page. No coupling edges to other stories.

### Frontend API client usage

```typescript
import { getCaseDetail } from '@/lib/api/cases'

const detail = await getCaseDetail(scenarioId, clientId)
// detail.client.name → string
// detail.invoices → InvoiceSummary[]
// detail.payments → PaymentSummary[]
// detail.communications → CommunicationSummary[]
// detail.score → ScoreSummary | null
```

### Page structure

```typescript
// [locale]/cases/[clientId]/page.tsx
export default async function CaseDetailPage({ params: { clientId } }: Props) {
  const t = await getTranslations('caseDetail')
  const scenario = await getActiveScenario()
  if (!scenario) return <NoActiveScenario />
  const detail = await getCaseDetail(scenario.id, clientId)
  return (
    <MainLayout>
      <CaseDetail detail={detail} />
    </MainLayout>
  )
}
```

## Acceptance Criteria

| ID | Severity | Description |
|----|----------|-------------|
| AC1 | MUST | `GET /api/v1/scenarios/{scenarioId}/clients/{clientId}` returns CaseDetailResponse with profile, invoices, payments, communications, and score sections |
| AC2 | MUST | The endpoint returns 404 for unknown scenario_id or client_id |
| AC3 | MUST | Invoices sorted by due_date desc, payments by payment_date desc, communications by created_at desc |
| AC4 | MUST | Communications array is empty (not null) when no comms exist |
| AC5 | MUST | Score section is null when no score exists for the client |
| AC6 | MUST | `ICommunicationRepository.get_by_client_id` returns communications ordered by created_at desc |
| AC7 | MUST | Case detail page at `[locale]/cases/[clientId]` renders all sections from real API data |
| AC8 | SHOULD | Case detail page shows loading state (skeleton) while resolving the active scenario |
| AC9 | MUST | Error state on the detail page shows a friendly message and a link back to cases list |
| AC10 | MUST | Each case row in the operations table links to its detail page |
| AC11 | MUST | All labels via next-intl caseDetail namespace; es.json/en.json key sets identical |
| AC12 | MUST | vitest green; tsc, eslint, prettier clean; pytest + mypy + ruff green for backend changes |
| AC13 | MUST NOT | No new hardcoded user-facing strings in modified files |
