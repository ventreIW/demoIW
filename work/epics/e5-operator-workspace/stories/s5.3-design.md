# Feature: Contact Result Form (Frontend)

> **Epic**: E5 — Operator Workspace
> **Complexity**: Simple | **SP**: 3

---

## 1. What & Why

**Problem:** The operator viewing a case detail has no way to record the outcome of a contact attempt. The backend endpoint (`POST /api/v1/scenarios/{id}/clients/{client_id}/contact-result`) was built by Nano and merged to main, but the UI action is missing — the operator must leave the app to record results.

**Value:** The operator can complete the full contact workflow from the case detail: see the case → record contact result → see score update immediately. First end-to-end operator → intelligence loop in the UI.

---

## 2. Approach

**How we'll solve it** (high-level):

A self-contained `ContactResultForm` component added as a new section on the `CaseDetail` page. Follows the existing `useState` + `fetch` pattern used in `GenerateScenarioForm` and `CsvUpload`. No form library, no new dependencies.

**Components affected:**

| Component | Change | Purpose |
|-----------|--------|---------|
| `ContactResultForm.tsx` | **create** | Form with type dropdown, notes textarea, record button, loading/error/success states |
| `lib/api/cases.ts` | **modify** | Add `recordContactResult()` API client function |
| `CaseDetail.tsx` | **modify** | Add `ContactResultForm` section + pass scenarioId/clientId; update score on success |
| `page.tsx` (case detail) | **modify** | Pass `scenarioId` down to `CaseDetailView` |
| `types/case-detail.ts` | **modify** | Add `ContactResultType` and `RecordContactResultResponse` types |
| `messages/en.json`, `es.json` | **modify** | Add contact result form i18n keys |
| `ContactResultForm.test.tsx` | **create** | Vitest tests for the form |
| `CaseDetail.test.tsx` | **modify** | Add test for ContactResultForm section |

**Lean design gates:**

| Gate | Assessment |
|------|-----------|
| **KISS** | `useState` only — no form library, no react-hook-form. Matches existing patterns. |
| **DRY** | Reuses existing `Select`, `Button`, `SelectContent`, `SelectItem` from `@/components/ui/` |
| **YAGNI** | No auto-save, no draft recovery, no undo. Record and done. |
| **MVP** | Dropdown + notes + record button + inline feedback. No contact history list. |

**Data mutations:** The endpoint returns 422 for invalid types (FastAPI enum validation), 404 for missing scenario/client. The API client throws on non-OK responses, the form displays the error inline. No silent drops.

**Legacy sweep:** Nothing — this is net-new (no V1 exists).

**Drift risk:** No drift risk identified — self-contained component, no coupling to other modules.

**Supply chain:** N/A — no new external dependencies.

## 3. Interface / Examples

> **IMPORTANT**: Provide concrete examples — these are critical for AI code generation accuracy

### API Client Usage

```typescript
const result = await recordContactResult(scenarioId, clientId, {
  contact_result: 'promise_to_pay',
  notes: 'Client will pay Friday',
})
// result.portfolio.score_value → 88.4 (updated)
```

### Component Usage

```tsx
<ContactResultForm
  scenarioId={scenarioId}
  clientId={clientId}
  onSuccess={(portfolio) => setUpdatedScore(portfolio.score_value)}
/>
```

### Expected Output

**Success (201):** Show confirmation message, update score display with new value from response.

**Error (422 — invalid type):** Inline error: "Invalid contact result type"
**Error (500/network):** Inline error: "Failed to record contact result"

### Data Structures

```typescript
// New types to add to types/case-detail.ts
export type ContactResultType =
  | 'promise_to_pay'
  | 'partial_payment'
  | 'no_answer'
  | 'disputed'
  | 'paid'

export interface RecordContactResultRequest {
  contact_result: ContactResultType
  notes?: string
}

export interface ClientScoreEntry {
  client_id: string
  client_name: string
  score_value: number
  category: string
  explanation: string
}

export interface RecordContactResultResponse {
  scenario_id: string
  client_id: string
  portfolio: {
    scores: ClientScoreEntry[]
  }
}
```

## 4. Acceptance Criteria

### Must Have

- [ ] AC1: ContactResultForm renders with type dropdown (5 ContactResultType options), notes textarea, and Record button
- [ ] AC2: Submitting a valid result calls `POST /api/v1/scenarios/{id}/clients/{client_id}/contact-result` with `{ contact_result, notes }` and shows success feedback
- [ ] AC3: Score display updates optimistically after successful record (from response portfolio)
- [ ] AC4: Button disabled + spinner during submission; inputs disabled while loading
- [ ] AC5: Network/server error (422/500/network) displayed inline, not as toast
- [ ] AC6: All Vitest tests pass; typecheck + lint + format clean
- [ ] AC7: i18n keys added for both es/en for all form labels, options, and messages

### Should Have

- [ ] Notes field is optional — form works without it

### Must NOT

- [ ] No auto-submit when selecting a type (operator must click Record)
- [ ] No toast notifications for errors (use inline messages per existing CsvUpload pattern)

<summary><h2>5. Detailed Scenarios</h2></summary>

### Scenario 1: Record a contact result — success

```gherkin
Given the operator is viewing a case detail page
When the operator selects "Promise to Pay" from the contact result dropdown
And enters "Client will pay Friday" in the notes field
And clicks "Record Contact"
Then the button shows a loading spinner and is disabled
And a POST request is sent to the contact-result endpoint
And the button returns to normal state
And a success message "Contact recorded" is shown
And the score display updates to the new value from the response
```

### Scenario 2: Invalid contact result type

```gherkin
Given the operator is viewing a case detail page
When the API returns a 422 error for invalid contact result type
Then an inline error message is shown: "Invalid contact result type"
And the button re-enables
And the form inputs remain editable
```

### Scenario 3: Network error

```gherkin
Given the operator is viewing a case detail page
When the API request fails with a network error
Then an inline error message is shown: "Failed to record contact result"
And the button re-enables
And the form inputs remain editable
```

### Scenario 4: Notes field is optional

```gherkin
Given the operator is viewing a case detail page
When the operator selects "No Answer" from the contact result dropdown
And leaves the notes field empty
And clicks "Record Contact"
Then the request is sent with notes: null
And the response is handled successfully
```
