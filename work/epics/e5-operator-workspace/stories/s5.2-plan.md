## Execution Order

```
Task 1 (backend repos) ──→ Task 2 (aggregate endpoint)
                              │
Task 3 (frontend types + i18n) ──→ Task 4 (detail page + component)
                                      │
                                      └─→ Task 5 (CaseTable link + manual integration)
```

**Rationale (risk-first):** Task 1 first because it's backend infrastructure that everything else depends on. Task 3 (types + i18n) is independent and could run in parallel with Task 1 conceptually, but sequential execution is cleaner. Task 2 (aggregate endpoint) is the highest-risk backend change (new composition logic). Task 4 (detail page) is the highest-risk frontend change (new component). Task 5 (navigation link + manual test) is last to verify the full flow.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Test infrastructure missing httpx/aiosqlite | Install via pip in Task 1; fallback to direct pytest commands |
| Circular import in sqlalchemy version | Pin sqlalchemy version in requirements; use `cd backend && python -m pytest` directly |
| `get_by_client_id` on payments needs invoice join | Follow existing `get_by_scenario_id` pattern that already joins through InvoiceORM→ClientORM |
| Score not yet scored for a client | AC5 ensures score is null (not a crash) when no score exists |
| `useFormatter` for dates not available in test | `renderWithIntl` already wraps with `NextIntlClientProvider` per s4.7 pattern |
