# S5.3 Scope — Contact Result + Status Update (→ Rescore)

**Status:** Active — authorized (Gustavo, 2026-07-27). Depends on s5.2 (done), E4 s4.6 (done).
**Size:** S · **Owner:** Nano (backend)

## In Scope
- `IContactResultRepository` port + `SQLAlchemyContactResultRepository` adapter (over existing `ContactResultORM` + mappers)
- `RecordContactResult` use case: persist `ContactResult` → update client status → call E4 rescore endpoint → return updated portfolio
- `POST /api/v1/clients/{client_id}/contact-result` endpoint with `ContactResultRequest` (contact_result_type, notes)
- Container provider `get_record_contact_result_use_case` wiring repos + rescore use case
- Tests: persist contact result, trigger rescore, 404 on unknown client, 422 on invalid result type
- Idempotency: re-recording a contact result creates a new audit row (append-only; no overwrite)

## Out of Scope
- Frontend UI action (Renata; separate s5.3 frontend task)
- Changing the rescore logic (E4 s4.6 owns that)
- Real message delivery (demo: "send" = status `sent` + audit row; no external transport)
- Multi-operator auth / roles (parking lot)

## Done when
- [ ] `POST /api/v1/clients/{client_id}/contact-result` persists a ContactResult and returns updated prioritized portfolio
- [ ] Response includes the re-ranked portfolio with the client's adjusted score
- [ ] 404 when client_id not found
- [ ] 422 when contact_result_type is invalid (not in ContactResultType enum)
- [ ] Re-calling creates a new audit row (append-only)
- [ ] Container exposes the use case; all new tests pass; ruff/format/mypy clean on touched files
- [ ] Epic acceptance gate: "Operator can record a contact result and update status" + "Recording a result calls the E4 rescore endpoint and the score updates" (RF-05.3–4, RF-02.5)
