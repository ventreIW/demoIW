# Retrospective: S5.4 — Communications Generator Backend

**Dates:** 2026-07-31 → 2026-07-31 (same day)
**Estimated:** 5 SP | **Actual:** ~5 SP

## Summary

Implemented the Communications Generator backend for the Operator Workspace (E5). The endpoint `POST /api/v1/scenarios/{scenario_id}/clients/{client_id}/communications` generates AI-assisted draft communications via OpenRouter, with channel (email/phone/WhatsApp) and tone (formal/firm/urgent) selection. Every draft is persisted with DRAFT status for audit.

**Key deliverables:**
- Prompt template: `prompts/communications/v1_draft.txt`
- `CommunicationDraftService`: prompt building + LLM call
- `GenerateCommunicationDraft` use case: validate → fetch aggregate → generate → persist
- Shared `fetch_case_aggregate()` service (single source of truth for router + use case)
- Router endpoint with proper error handling (404, 502)
- 9 router/contract tests + 3 integration tests (mocked OpenRouter via respx)

All 405 tests pass, mypy strict clean, ruff clean.

## What went well

1. **Single source of truth for case aggregate**: Extracted `fetch_case_aggregate()` to a shared service (`case_aggregate_service.py`) used by both the router (`GET /cases/{sid}/clients/{cid}`) and the new use case. This eliminated ~40 lines of duplicate logic and ensures consistency.

2. **Config-driven prompt template**: Following the `prompts/data_enrichment/` pattern, the prompt lives in `prompts/communications/v1_draft.txt` — editable without code changes.

3. **Proper error handling**: Added `ExternalServiceError` catch in router → 502 Bad Gateway when OpenRouter fails (after retries). This matches the pattern established in s4.8 (enrichment degradation).

4. **Comprehensive test coverage**: 
   - 10 unit tests for `CommunicationDraftService`
   - 6 unit tests for `GenerateCommunicationDraft` use case
   - 9 router/contract tests (201, 422, 404, all channels/tones)
   - 3 integration tests with mocked OpenRouter (success, 500→502, multiple independent calls)

4. **Container provider ordering**: Followed PAT-N-4 correctly — `get_draft_service` defined before `get_generate_communication_draft_use_case` which depends on it.

5. **Integration test realism**: Mocked OpenRouter at HTTP layer via respx (not at adapter level), exercising real serialization, retries, and error handling. Verified draft persistence by fetching case detail after creation.

## What to improve

1. **OpenRouterAdapter retry logic in tests**: The integration tests revealed that `respx` with `side_effect` and `TimeoutException` doesn't properly exercise the adapter's retry logic (respx wraps exceptions in `SideEffectError`). Documented this limitation in tests — the 500/timeout tests work but the actual retry count verification is limited by test tooling.

2. **Malformed JSON handling**: `OpenRouterAdapter` doesn't catch `JSONDecodeError` (only `HTTPStatusError` and `TimeoutException`), so malformed responses propagate as 500. This is a pre-existing gap, not introduced here, but worth noting for future hardening.

3. **Scenario setup boilerplate**: The `_setup_scenario_with_client()` helper (generate → active → score → prioritized) is verbose. Could extract to a shared test utility.

4. **Prompt template versioning**: The template is `v1_draft.txt` but no version in the prompt itself. Could add a comment/header with version for traceability.

## Heutagogical Checkpoint

1. **What did I learn?**
   - The `fetch_case_aggregate()` pattern is powerful — reusing it in both router and use case eliminated a major source of bugs (divergent data fetching).
   - `respx` mocking at HTTP layer is superior to mocking adapters — catches serialization, retries, error handling.
   - The "500 after retries → 502" pattern from s4.8 applies cleanly here via `ExternalServiceError`.

2. **What would I change about the process?**
   - Start integration tests earlier (after T4) to catch seams sooner.
   - Add a shared test utility module for common setup (`_setup_scenario_with_client`).
   - Document OpenRouterAdapter retry behavior more explicitly in the skill references.

3. **Framework improvements?**
   - Add a `test_helpers.py` module pattern to RaiSE templates for shared test setup.
   - Consider a `rai graph query` for "integration test patterns with mocked external services" to surface the respx patterns automatically.

4. **More capable of now?**
   - Building LLM-integrated endpoints with proper error handling, retries, and audit persistence.
   - Refactoring duplicate data-fetching logic into shared services without breaking existing consumers.

## Patterns added / reinforced

### New patterns (to persist):
1. **Shared case aggregate service** — Extract `fetch_case_aggregate()` to a service used by both router and use cases. Single source of truth for composed data.
   - Context: `case-aggregate, shared-service, router-use-case-reuse, s5.4`

2. **LLM prompt as config file** — Store prompts in `prompts/{domain}/v{N}_name.txt`, load at service init. Enables iteration without code changes.
   - Context: `llm-prompt-config, config-driven, s5.4`

3. **500-after-retries → 502 pattern** — Catch `ExternalServiceError` in router and return 502. LLM adapter handles retries internally.
   - Context: `llm-error-handling, 502-bad-gateway, external-service-error, s4.8, s5.4`
