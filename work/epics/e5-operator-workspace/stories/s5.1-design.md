# s5.1 Design — Operations Panel (Prioritized Case List)

**Story:** s5.1 · **Epic:** E5 Operator Workspace · **Branch:** `story/s5.1/operations-panel-case-list`
**Complexity:** Moderate (4 logical components, 0 new external dependencies, trivial algorithms)
**Date:** 2026-07-28 · **Author:** Rodrigo

---

## Problem

E4 produces a ranked collections queue but no human can see it. The operator (P-01) has no surface
at all: `GET /scenarios/{id}/prioritized` returns JSON and the sidebar's *Operaciones* link points
at `#`. Worse, the endpoint cannot express two of the five columns the operator needs — the payload
carries no client **name** and no **days overdue**, so a row could only ever show a UUID.

## Value

First end-user surface of the demo, and the walking skeleton that proves the frontend↔E4 payload
seam before s5.2 builds the case-detail hub on top of it. Turns "158 de 271 cuentas concentran 80%
del valor" from a log line into something a collector can act on.

## Gemba walk — what the code actually says

Read before designing: `backend/app/routers/scenarios.py:350-484`,
`domain/value_objects/prioritized_case.py`, `application/services/prioritizer.py`,
`application/use_cases/{score_scenario,prioritize_scenario}.py`,
`adapters/persistence/sqlalchemy_scenario_repo.py:124-190`,
`frontend/src/app/[locale]/scenarios/page.tsx`, `components/scenarios/ScenarioGrid.tsx`,
`lib/api/scenarios.ts`, `components/layout/MainLayout.tsx`, `test-utils/i18n.tsx`.

### Finding 1 — the contract gap is confirmed
`PrioritizedCase` (`prioritized_case.py:53-70`) carries `client_id, score, outstanding, rank,
category` and derives `expected_recoverable`. No `name`, no `days_overdue`. The scope's suspicion
was correct.

### Finding 2 — `days_overdue_min` and `sort=days_overdue` are dead code (latent bug)
The endpoint advertises both (`scenarios.py:364-367`) and implements them as:

```python
cases = [c for c in cases if getattr(c, "days_overdue", 0) >= days_overdue_min]   # :436
"days_overdue": lambda c: getattr(c, "days_overdue", 0),                          # :444
```

`PrioritizedCase` has no such attribute, so the fallback `0` always wins. Consequences:
- `?days_overdue_min=30` evaluates `0 >= 30` for every case → returns an **empty portfolio**, not a filtered one.
- `?sort=days_overdue` is a no-op — every sort key is `0`.

`tests/test_prioritized_endpoint.py:214-232` covers this and passes, because it asserts only
`status_code == 200` and never that filtering occurred. A test that asserts the endpoint *responds*
rather than that it *works*.

**This story fixes the bug as a byproduct, not as scope creep:** the same field that makes the UI
column possible is the field whose absence breaks the filter. Adding it and leaving the filter
untested would knowingly ship a lie. Cost is one real assertion.

### Finding 3 — the data exists upstream, nothing new to compute
- `name` — `ClientORM.name` is non-nullable; already in `clients_df` (`sqlalchemy_scenario_repo.py:163`).
- `days_overdue` — `days_overdue_max` is an existing model feature over **open** invoices
  (`feature_extractor.py:142`), already a column of `training_set.X`.

Both are per-client values available exactly where `outstanding_by_client` is already assembled.

### Finding 4 — the frontend pattern is established, follow it
Server component page → `getTranslations` → `MainLayout` → try/catch error branch → presentational
child. `ScenariosPage` is the template. Tests use `renderWithIntl` from `test-utils/i18n.tsx`, which
loads the real `es.json`/`en.json`, so a missing key fails the test — that is the i18n guard.

### Finding 5 — active scenario has two competing sources of truth
`ScenariosPage` reads a cookie `active_scenario_id`; the backend persists status via
`repo.set_active` and returns `status: "active"`. The cookie is a scenarios-page UI convenience;
the **backend is the durable truth**. s5.1 resolves the active scenario from `listScenarios()` by
`status === 'active'`. Reconciling the cookie is out of scope (parking lot).

### Legacy sweep (mandatory)
**Net-new frontend; extension backend — one small V1 removal.** The `getattr(c, "days_overdue", 0)`
fallbacks at `scenarios.py:436` and `:444` become dead defensive code once the field exists and
**must be deleted in the same commit**, replaced by direct `c.days_overdue`. Leaving them would
preserve a silent-zero path that hides the exact class of bug this story fixes. No other V1 is
orphaned: no component, page, or route is superseded.

### Drift risk
`governance/drift-hotspots.json` and `drift-catalog.md` are absent project-wide → ranked-hotspot
step skipped (graceful degradation). Manual AG-assessment:
- **AG4 (context-window fan-out):** 5 backend files across domain→application→adapter, but along
  one existing dependency chain already traversed by `outstanding_by_client`. No unresolved coupling.
- **AG2 (clone amplification):** none — the case table is the first of its kind; no duplication of
  `ScenarioGrid` (different shape, different concern).

### Supply chain gate
**N/A.** No new dependency. Everything used (next-intl, React, FastAPI, Pydantic, pandas, shadcn/ui
primitives) is already in the project.

## Approach

Thread the two missing attributes through the **existing** per-client dictionary pattern on
`ScoringRun`, then render a server-side table. No new abstraction, no new service, no new endpoint.

**Why threading and not a router-level join:** `ScoringRun`'s own docstring states its purpose —
"prioritisation has one input object and the system keeps **one** definition of exposure". Joining
names in the router would put presentation assembly in the transport layer and give the rescore
endpoint (which returns the same response model) a second, divergent path. Threading gives both
endpoints the fields for free.

**What the layer earns (value preservation):** `days_overdue` is not a pass-through rename — it is a
*decision* that the operator-facing number is the **maximum across open invoices**, not the mean and
not a per-invoice value. That domain choice belongs in the domain object, which is why the field
lives on `PrioritizedCase` rather than being computed in the view.

### Design decisions

**D1 — `days_overdue` is the max over open invoices.**
Source is the existing `days_overdue_max` feature. For an operator triaging a call, "the oldest
thing this client owes" is the actionable number; a mean would understate a badly aged account by
averaging it against recent invoices. Serialized as `int` — the ORM column is `Integer` and the
UI shows whole days; carrying float precision would be false precision.

**D2 — Missing name or days-overdue is an error, not a default.**
Reuses the guard `prioritize()` already applies to exposure (`prioritizer.py:56-60`). Every scored
client comes from the same training set, so absence means an upstream bug. Defaulting to `""` or
`0` would reproduce exactly the silent-zero failure of Finding 2.

**D3 — The list renders `cases` (full portfolio), not `pareto_subset`.**
The scope asks for the prioritized case list, rank-ordered. Showing only the Pareto subset would
hide accounts without the operator asking. The `summary` line is displayed as context (SHOULD).

**D4 — Active scenario resolved from backend status, not the cookie.** See Finding 5.

**D5 — No pagination, no sort/filter controls.** Per scope. Demo scenarios are ~hundreds of rows;
the API supports sorting and filtering, and wiring UI controls is parked for later polish.

## Acceptance criteria

### MUST

| ID | Criterion |
|---|---|
| AC-1 | `GET /scenarios/{id}/prioritized` returns `client_name` (non-empty) and `days_overdue` (int ≥ 0) on every case in both `cases` and `pareto_subset` |
| AC-2 | `?days_overdue_min=N` returns only cases with `days_overdue >= N`, asserted against real generated data — **not** merely a 200 |
| AC-3 | `?sort=days_overdue&order=desc` returns cases in non-increasing `days_overdue` order |
| AC-4 | `/[locale]/cases` renders one row per client, rank-ordered, showing client name, outstanding, days overdue, score, category |
| AC-5 | Empty portfolio, no-active-scenario, and API-error states each render a message — no crash, no blank table |
| AC-6 | Every visible string comes from next-intl; `es.json` and `en.json` key sets are identical |
| AC-7 | Both `getattr(c, "days_overdue", 0)` fallbacks deleted from `routers/scenarios.py` |
| AC-8 | Gates green: pytest, mypy, ruff (backend); vitest, tsc, eslint, prettier (frontend) |

### SHOULD

| ID | Criterion |
|---|---|
| AC-9 | The portfolio `summary` line renders above the table as concentration context |
| AC-10 | Sidebar *Operaciones* links to `/cases` instead of `#` |
| AC-11 | Category renders as a localized badge (Alta/Media/Baja), not the raw English enum |

### MUST NOT

| ID | Criterion |
|---|---|
| AC-12 | MUST NOT add sort/filter UI controls, pagination, or case-detail navigation (s5.2) |
| AC-13 | MUST NOT default a missing name or days-overdue to a placeholder — absence raises |
| AC-14 | MUST NOT change ranking, `expected_recoverable`, the Pareto algorithm, or the threshold |
| AC-15 | MUST NOT make `/prioritized` read persisted scores (parked E4 follow-up) |
