**Dates:** 2026-07-27 (single session)
**Estimated:** S (2 tasks) | **Actual:** S — 2 tasks, one small mismatch (EntityNotFoundError arity), no rework

## Summary
Closed the M4 gap: `POST /api/v1/scenarios/{id}/score` scores an active scenario and persists a
`Score` per client via `IScoreRepository` (`ScoreAndPersistScenario` use case + endpoint + container
provider). Idempotent — re-calling returns the persisted count without duplicating rows. Backend
337 → 344 tests. Epic acceptance gate #1 is now **satisfiable** (the mechanism exists and is tested).

## What went well
- **M4 earned its keep:** the checkpoint surfaced that scores were computed live but never persisted —
  a gap that unit tests with mocks had happily passed for three stories. This story only exists because
  M4 checked observable state, exactly as the epic scope demanded after E3's miss.
- **Thin orchestration, zero new logic:** reused `ScoreScenario` + `add_many` unchanged; the story is
  a wire, not a rebuild.
- **Idempotency guard** (get_by_scenario before insert) closed the one real correctness risk
  (duplicate Score rows) with no new repo method.

## What to improve
- **The prioritized endpoint still re-scores live** and ignores the now-persisted scores (its comment
  even says "since s4.9 not done yet"). Left untouched by scope discipline, but it's now genuinely
  stale — a follow-up should make it read persisted scores (perf + single source of truth).
- **EntityNotFoundError arity** (`(entity_type, entity_id)`) tripped the first GREEN — a 30-second fix,
  but a reminder to check a shared exception's signature during gemba, not at the type gate.

   caught this; this story is the process working as designed.
