# Story: Score Persistence Wiring — score an active scenario and persist

## User Story
As the **intelligence engine**,
I want **a step that scores an active scenario and persists every client's Score through
`IScoreRepository`**,
so that **the epic's gate "every client in an active scenario has a persisted Score" is actually
met — today scores are only computed in-memory by the prioritized endpoint and never stored.**

## Context (why this story exists)
M4 verification found gate #1 unmet: `ScoreScenario` computes `Score` entities and the prioritized
endpoint re-scores live on every call (`scorer = ScoreScenario()`), but **nothing persists**. s4.9
delivered `IScoreRepository` + adapter; this story wires scoring → persistence.

## Acceptance Criteria

### Scenario: Score an active scenario and persist every client's Score
```gherkin
Given an active scenario with scorable clients
When POST /api/v1/scenarios/{id}/score is called
Then a Score is persisted for every scored client (value, category, explanation)
And the response reports the scored and unscored client counts
And get_by_scenario(id) returns those scores
```

### Scenario: Scoring is not duplicated on repeat calls
```gherkin
Given a scenario whose scores are already persisted
When POST /api/v1/scenarios/{id}/score is called again
Then no duplicate Score rows are created
And the response reflects the already-persisted count
```

### Scenario: Scenario with no data
```gherkin
Given a scenario id that has no dataset
When POST /api/v1/scenarios/{id}/score is called
Then the endpoint returns 404 (nothing to score)
```

## Examples (Specification by Example)
| Input | Action | Expected |
|---|---|---|
| active scenario, 60 scorable clients | `POST /{id}/score` | 201; `scored_count=60`; 60 rows via `get_by_scenario` |
| same scenario, already scored | `POST /{id}/score` again | 200/201; `scored_count=60`; still 60 rows (no dupes) |
| unknown / dataless scenario | `POST /{id}/score` | 404 |

## Notes
- Reuses `ScoreScenario.execute(dataset, scenario_id, seed)` and `IScoreRepository.add_many`
  (both exist). New: a thin `ScoreAndPersistScenario` use case + endpoint + container provider.
- Idempotency: if `get_by_scenario` is non-empty, return the existing count without re-inserting
  (avoids duplicate rows; replace-on-rescore is E5's concern, parked).
- Out of scope: changing the prioritized endpoint to read persisted scores (it keeps scoring live);
  E5 operations panel; migrations (table exists).
