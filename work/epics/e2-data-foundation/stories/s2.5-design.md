# s2.5 — CSV Upload Backend · design

> ⚠ **RETROACTIVE RECONSTRUCTION — written 2026-08-20, not 2026-07-01.**
> No design existed for s2.5: `s2.5-plan.md` goes straight from the user story to a task
> list. This document reconstructs the design decisions from the merged code so the
> methodology record is complete, and records what the missing design phase cost — which
> turned out to be substantial. It is **not** evidence that a design guided the work.

**Story:** s2.5 — CSV Upload Backend · **Size:** S (3 SP) · **Epic:** E2
**Depends on:** s2.2 (`IScenarioRepository` + scenarios router pattern)

## Problem

A demo facilitator needs to create a scenario from an external CSV of receivables, without
hand-crafting API calls or waiting on the procedural generator.

## Approach as built

`POST /api/v1/scenarios/upload-csv` accepts a multipart file with the columns
`client_name, amount, due_date, invoice_id`, validates the header, and persists a `Scenario`
plus one `Client` and one `Invoice` per row through
`SqlAlchemyScenarioRepository.create_from_csv`.

## Decisions, as recoverable from the code

| # | Decision | Where |
|---|---|---|
| D1 | One client per CSV row — no de-duplication by `client_name` | `create_from_csv` |
| D2 | `days_overdue` computed at ingest as `max(0, now - due_date)` | `create_from_csv` |
| D3 | Every client gets `PaymentPattern.ON_TIME` — a CSV carries no payment history | `create_from_csv` |
| D4 | Client and invoice ids are fresh `uuid4()` | `create_from_csv` |
| D5 | Invoice status written as the literal `"pending"` | `create_from_csv` |
| D6 | Validation is header-shape only; malformed/empty/missing-column → 422 | router |

## What the missing design phase cost

**This is the substantive content of this document.** Two of the six decisions above were
wrong, and both were wrong in a way a gemba walk would have caught, because both required
only reading the code that consumes the data:

- **D5 produced BUG-03 (S1).** `"pending"` matches neither branch of `FeatureExtractor`, which
  partitions on `status == "overdue"` (open) and `status == "paid"` (settled). Every uploaded
  invoice was invisible to both, outstanding summed to zero, and **the entire CSV feature
  produced scenarios no downstream module could use** — for roughly seven weeks, until
  2026-08-20. There was no `InvoiceStatus` enum to violate; the value was a bare string, and
  nothing checked it. A design step that read `feature_extractor.py` would have found the
  vocabulary in under a minute.

- **D3 produced BUG-06, which is still open.** Assigning `ON_TIME` to every client is a
  reasonable default in isolation, but `OutcomeLabeller` simulates the training label *from*
  `payment_history_pattern`, so a constant pattern yields a single label class and training
  aborts. Unlike D5 this is not a one-line fix: deriving the pattern from observable ageing
  is the leakage ADR-006 forbids, and randomising it trains a confident model on noise. It
  needs an ADR on how unlabelled uploads get scored.

Both defects are properties of the **seam** between this story and E4's scoring pipeline —
precisely what a design phase's gemba walk exists to inspect, and precisely what a task list
starting at "T1 — CSV upload endpoint + happy path" cannot surface.

The tests did not compensate: all four original s2.5 tests assert on the *upload response*
(201, and 422 for three malformed inputs). None asked whether the persisted scenario could
subsequently be used, so the feature was verified up to the moment of writing and not one step
past it.

## Consequence for the record

s2.5 is the clearest evidence in this project that the design phase is not ceremony. It is the
only story missing a design, and it is the origin of one S1 defect that disabled a shipped
feature for seven weeks plus one still-open architectural gap. See `work/bugs/BUG-03/` and the
BUG-06 entry in `dev/parking-lot.md`.
