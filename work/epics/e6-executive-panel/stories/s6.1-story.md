# Story: KPI Aggregation — Backend

## User Story
As the **finance director (P-02)**,
I want **one endpoint that states what the receivables book is worth and where the value sits**,
so that **I can judge the portfolio in a single view instead of reading a 271-row queue built for someone else's job.**

## Acceptance Criteria

### Scenario: KPI endpoint returns every RF-06.1 figure for a scored scenario
```gherkin
Given a scenario with persisted scores
When GET /api/v1/scenarios/{scenarioId}/kpis is called
Then the API returns 200 with
  - scenario (id, name, sector) and scored_at from the persisted scoring run
  - client_count
  - total_outstanding — open invoices net of partial payments
  - total_expected_recoverable — sum of outstanding x score/100
  - collected_to_date — payments against settled invoices
  - recovery_rate_actual and recovery_rate_expected, as separate figures
  - cases_by_category keyed by every ScoreCategory member
```

### Scenario: Segmentation breaks the portfolio down three ways
```gherkin
Given a scenario with persisted scores
When GET /api/v1/scenarios/{scenarioId}/kpis is called
Then the response carries a segmentation object with keys
  days_overdue_bucket, amount_range and score_category
And every bucket carries label, client_count, outstanding and expected_recoverable
And the client_count across the buckets of each dimension sums to client_count
```

### Scenario: An unscored scenario is refused, not answered with zeros
```gherkin
Given a scenario that exists but has no persisted Score rows
When GET /api/v1/scenarios/{scenarioId}/kpis is called
Then the API returns 409
And the message names POST /api/v1/scenarios/{scenarioId}/score as the fix
```

### Scenario: Unknown scenario
```gherkin
Given a scenario id that does not exist
When GET /api/v1/scenarios/{scenarioId}/kpis is called
Then the API returns 404
```

### Scenario: Money is not double-counted for a partial payer
```gherkin
Given a client with one open invoice of 10,000 against which 4,000 has been paid
When the KPI aggregate is computed
Then that client contributes 6,000 to total_outstanding
And the 4,000 does not appear in collected_to_date, because the invoice is not settled
```

### Scenario: Category counts are built from the enum, not from strings
```gherkin
Given a portfolio containing high, medium and low scored clients
When the KPI aggregate is computed
Then cases_by_category contains a key for every ScoreCategory member, including any with a count of zero
And no count is derived from comparing a capitalised literal against an enum value
```

## Examples (Specification by Example)

A three-client scenario, all scored. Invoice `I3` is settled; the rest are open.

| Client | Invoice | Amount | Status | Paid | Days overdue | Score |
|---|---|---|---|---|---|---|
| A | I1 | 10,000 | overdue | 4,000 | 95 | 80 |
| B | I2 | 20,000 | overdue | 0 | 20 | 40 |
| C | I3 | 5,000 | paid | 5,000 | 0 | 90 |

| Figure | Expected | Why |
|---|---|---|
| `client_count` | 3 | every scored client, including C with nothing outstanding |
| `total_outstanding` | 26,000 | (10,000 − 4,000) + 20,000 + 0 |
| `total_expected_recoverable` | 12,800 | 6,000×0.80 + 20,000×0.40 + 0×0.90 |
| `collected_to_date` | 5,000 | only I3 is settled; A's 4,000 sits against an open invoice |
| `recovery_rate_actual` | 0.1613 | 5,000 / (5,000 + 26,000) |
| `recovery_rate_expected` | 0.4923 | 12,800 / 26,000 |
| `cases_by_category` | `{high: 2, medium: 0, low: 1}` | 80 and 90 are high, 40 is low — via `categorize()`, not string comparison |
| `days_overdue_bucket` | `90+`: A · `0-30`: B, C | C has no open invoice, so its max days overdue is 0 — the lowest bucket starts at 0 precisely so C is not dropped from the breakdown |

The A row is the important one: 4,000 has been paid, but the invoice is still open, so the money
is neither outstanding nor collected. A naive implementation counts it twice or loses it.

## Notes

- **ADR-009** governs this story: read persisted `Score` rows, never fit a model. Reuse
  `feature_extractor.outstanding_by_client()` for money rather than writing a second definition.
- **Follows the s5.4 pattern** (`case_aggregate_service.fetch_case_aggregate`): a module-level async
  function over repository ports returning a frozen dataclass, callable from both a router and a use
  case. s6.3's NL executor is the second caller (ADR-008), which is what keeps the dashboard and the
  NL answer from disagreeing.
- **Segmentation excludes sector** — it is an attribute of `Scenario`, not `Client`, so it is
  constant within a scenario. See `design.md` §Gemba G2 and `scope.md` §Open questions.
- **Two recovery rates, not one.** They answer different questions and are not a before/after pair.
  The definition is stated in `design.md` §KPI formulas and is awaiting Gustavo's confirmation; it is
  one function in one service if the answer differs.
- **Capture the real payload with `curl` before s6.2 writes a TypeScript type.** s5.1 shipped a
  defect through design, types, component and fixture because every layer inherited one assumption
  read from the domain classes. `?category=High` on `/prioritized` is the same species, still live.
