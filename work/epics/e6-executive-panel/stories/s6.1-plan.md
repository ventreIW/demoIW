## T1 — Domain: KPI value objects, bucketing, and the shared formula

**Size:** M · **Depends on:** — · **AC:** story AC 5, 6; design AC 3, 4, 5, 10, 11

Domain layer only. No I/O, no repositories — every figure computed from plain inputs, which is what
makes the arithmetic testable against hand-computed numbers.

**Files**
- `backend/app/domain/value_objects/prioritized_case.py` — modify: extract module-level
  `expected_recoverable(outstanding, score)`; `PrioritizedCase.expected_recoverable` delegates to it
  (design D2 — sweep the single call site in this same commit)
- `backend/app/domain/exceptions.py` — modify: add `PortfolioNotScoredError` (design D4)
- `backend/app/domain/value_objects/portfolio_kpis.py` — create: `SegmentBucket`, `PortfolioKpis`,
  the three bucket-assignment functions, and the two derived rate properties
- `backend/tests/unit/test_portfolio_kpis.py` — create

**TDD**
- **RED** — write the failing tests first:
  - the three-client worked example from `s6.1-story.md` §Examples, asserting all six figures with
    `pytest.approx` on the rates. The partial payer (A: 10,000 open, 4,000 paid) must contribute
    6,000 to outstanding and 0 to collected.
  - **totality**: for each of the three dimensions, the sum of bucket `client_count` equals the
    total client count. This is the assertion that cannot pass vacuously — write it before the
    bucketing code exists.
  - a client with 0 days overdue lands in the `0-30` bucket, not outside the dimension.
  - `cases_by_category` contains all three `ScoreCategory` members when one has zero clients.
  - degenerate portfolios: all-equal balances (quartile edges collapse), all-zero outstanding
    (both rates return 0.0, no `ZeroDivisionError`), single client.
  - `expected_recoverable(6000, 80) == 4800.0`, and `PrioritizedCase.expected_recoverable` returns
    the identical value — the delegation is asserted, not assumed.
- **GREEN** — implement. `amount_range` boundaries via `numpy.percentile`, assigned by comparison,
  **not** `pd.qcut` (design D5 — `qcut` raises on duplicate edges, which equal or zero balances
  produce).
- **REFACTOR** — the three `assign_*` functions share a shape; extract only if it reads better, not
  on principle.

Plus: `tests/unit/test_prioritized_case.py` and `tests/unit/test_prioritizer.py` still pass — they

## T4 — Manual integration + payload capture

**Size:** XS · **Depends on:** T3 · **AC:** design §Testing strategy

Verification against running software. Mocked unit tests cannot catch what this catches — E4's M4
found a generation-layer crash no unit test saw, and E5 repeated the lesson.

1. `cd backend && uvicorn app.main:app --reload`
2. Activate a scenario, `POST /{id}/score`, then `GET /{id}/kpis`.
3. **Check the arithmetic by hand** against the response: do the per-dimension counts sum to
   `client_count`? Is `total_expected_recoverable` ≤ `total_outstanding`? Does
   `cases_by_category` sum to `client_count`? A green suite that disagrees with the running app is
   the s5.1 failure mode.
4. Hit `/kpis` on an unscored scenario — confirm a 409 with an actionable message, not zeros.
5. **Capture the payload to `work/epics/e6-executive-panel/stories/s6.1-payload.json` and commit
   it.** This is the artifact s6.2 builds its TypeScript type from — not the design examples, and
   not the domain classes. s5.1 shipped `'High'` where the API sends `'high'` because the type, the
   component, the fixture and the tests all inherited one assumption read from the domain classes,
   and `?category=High` is still broken in this repo for the same reason.

**Verification:** payload committed; hand-checked sums recorded in the story progress notes.

## Execution order

```
T1 (domain) ──▶ T2 (service) ──▶ T3 (API) ──▶ T4 (manual)
```

Strictly sequential — each task's tests need the previous task's types. No parallelism available in
a story this size, and the dependency graph is a chain, so it is trivially acyclic.

**Risk-first within the chain:** T1 carries the arithmetic and the bucket-totality property, which is
where a defect would be both most likely and most expensive — it would propagate into s6.2's charts
and s6.3's NL answers, both of which read this aggregate. It is deliberately the largest task and
the one written entirely against hand-computed numbers.

## Risks

| Risk | Mitigation |
|---|---|
| Quartile boundaries collapse on a portfolio with many equal or zero balances, dropping or duplicating clients | T1 asserts totality on degenerate portfolios explicitly. Boundary comparison over `numpy.percentile`, never `pd.qcut` (design D5) |
| The `expected_recoverable` extraction breaks `/prioritized` | One call site, swept in the same commit; `test_prioritized_case.py` and `test_prioritizer.py` are the existing guard and must stay green |
| `payments_df` with no columns raises `KeyError` on a scenario with no payments | Explicit RED test in T2 (gemba S5) |
| Story exceeds S | `amount_range` is the dimension to cut — it is the most complex and the least demo-critical of the three. Cutting it still satisfies RF-06.2's "≥2" |
| Recovery-rate definition is unconfirmed by Gustavo | Built as two clearly-labelled properties; one function to change if the answer differs. Not blocking |
