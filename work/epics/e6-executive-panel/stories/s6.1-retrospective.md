## Summary

`GET /api/v1/scenarios/{id}/kpis` returns the six RF-06.1 figures and three segmentation
dimensions, reading persisted `Score` rows and never fitting a model (ADR-009). Verified live at
149 ms on a 120-client portfolio, with the sums hand-checked against the response rather than
against the fixtures.

## What went well

**The gemba walk changed the design before any code existed.** The epic design sketched a
five-repository composition. Reading `sqlalchemy_scenario_repo.py` showed `get_raw_dataset()`
already returns the three DataFrames `outstanding_by_client()` consumes — so the service composes
**two** ports and reuses the shared balance definition verbatim. The five-repo version would have
required either a DataFrame conversion or a second money calculation, which is precisely what
ADR-009 was written to prevent. That is design work that only reading the code produces.

**Bucket totality caught nothing — which is the point.** Writing "counts sum to `client_count`"
before the bucketing existed forced two decisions early that would otherwise have been defects: the
lowest ageing bucket starting at 0 rather than 1 (a scored client with no open invoices has max
days overdue of 0), and de-duplicating collapsed quartile labels so the bucket dict cannot silently
merge two bands. Both were designed in because the assertion made them visible, not patched in
after a failure.

**The 409 decision paid off immediately in the manual test.** Hitting `/kpis` on a fresh unscored
scenario returned a message naming `POST /score`. Under the zero-filling alternative it would have
rendered a $0 dashboard indistinguishable from a fully settled book.

**Three ADR-driven constraints held under implementation pressure** without needing to be revisited:
read persisted scores, reuse `outstanding_by_client()`, refuse rather than zero-fill.

## What to improve

**One RED failure was my test helper, not the implementation.** `_fetch(dataset=None)` fell through
to the default dataset via `dataset if dataset is not None else _dataset()`, so the no-data case
never reached the service and the test failed with "DID NOT RAISE". The implementation was correct
the whole time. Cost ~5 minutes, but it is the failure mode where a test helper's convenience
default silently disarms the case it exists to exercise — worth naming because a *passing* version
of that bug is invisible.

**`dict.fromkeys(ScoreCategory, 0)` types as `dict[str, int]`, not `dict[ScoreCategory, int]`.**
`StrEnum` members widen to `str` through `fromkeys`. mypy caught it; an explicit comprehension fixed
it. Worth knowing before the next enum-keyed aggregate.

**`conftest.py` needed a refactor this story did not plan for.** The `client` fixture created its
engine locally, so seeding was impossible without either duplicating ~20 lines or restructuring.
Extracting a shared helper was the right call and the 412 existing tests stayed green, but touching
a shared test fixture inside a story sized S is a scope risk the plan should have named.

**The manual test ran on SQLite again.** Third story in a row. No Postgres, no Docker in this
environment. E4 deferred it, E5 closed with it open and pushed it to E7 — this story could not close
it either.

## Heutagogical Checkpoint

**1. What did I learn?**
That "reuse the existing definition" is a *data-shape* constraint, not just an intention.
`outstanding_by_client()` takes DataFrames. Any design that reached it through entity repositories
would have had to convert or re-derive — so the ADR's requirement effectively dictated which
repository methods the service could call. I would not have seen that from the port interfaces
alone; it came from reading the adapter.

**2. What would I change about the process?**
Write the test *helpers* with the same suspicion as the assertions. The `_fetch(dataset=None)` slip
happened because the helper's ergonomics were designed before the cases were. Concretely: when a
helper takes an argument whose `None` is meaningful, reach for a sentinel first rather than after
the confusing failure.

**3. Framework improvements?**
Three, all filed in `dev/parking-lot.md`:
- `rai graph query` fails outright with `OperationalError: no such column: data_json` — the graph DB
  predates the installed CLI's schema. PRIME's tier-1 queries have now degraded to no-ops for two
  consecutive epics, so every "surface retrieved patterns" step this session returned nothing.
- `.raise/rai/learnings/` still does not exist project-wide, so this skill's Step 3 chain-read has
  nothing to aggregate. Standing since E4.
- `rai-story-implement`'s embedded pitfalls include a **git-identity rule from another developer's
  session** demanding commits be authored by `bernardo-525`, with an instruction to STOP if the
  identity is `ventreIW`. `ventreIW` is this repository's owner. Followed literally it blocks the
  legitimate author from committing. Skill pitfalls captured from one session are being replayed as
  universal rules.

**4. What am I more capable of now?**
Recognising the vacuous-assertion defect species *before* writing the test, rather than diagnosing
it after. This codebase has produced three instances (s5.1's `days_overdue` filter, `?category=High`,
and the empty-loop tests that hid both). The general form is: an assertion whose subject can be
empty, or is computed from a different object than the one under test. The counter-move is an
assertion over a total, which has no empty-set escape hatch.

## Improvements applied

- Bucket totality asserted as a sum across all three dimensions, in the domain **and** over the wire
  (serialisation can lose a bucket that the domain produced).
- The no-model-fit acceptance criterion written as an AST check over the module's imports rather
  than a substring grep — s4.4 wrote the same AC as a grep and it flagged a docstring describing the
  rule.
- `client_with_db` fixture added so integration tests seed with direct ORM inserts (PAT-R-10, filed
  at E5 close and applied here for the first time). `test_case_detail_endpoint.py` states in its own
  docstring that it could only assert 404s for want of exactly this.
- Real payload captured with `curl` and committed as `s6.1-payload.json`, so s6.2 builds its
  TypeScript type from an observed response rather than from the domain classes — the exact path by
  which s5.1 shipped `'High'` against an API that sends `'high'`.

## Patterns added

| Type | Pattern |
|---|---|
| technical | Extract a shared formula to a module-level function the moment a second consumer needs it without the object that owns it |
| process | Assert that per-bucket counts sum to the total, not that each bucket's contents match a predicate — predicate assertions over possibly-empty results pass vacuously |
| technical | Prefer `numpy.percentile` boundary comparison over `pandas.qcut` for quantile bucketing — `qcut` raises on the duplicate edges that equal or zero values produce |
| process | Give integration tests a fixture exposing a session maker onto the same test database, so they seed with ORM inserts instead of driving an LLM-backed endpoint |
| architecture | Refuse rather than zero-fill when a precondition is unmet — zeros make "unmet" and "genuinely empty" indistinguishable to the reader |

surfaced at PRIME to evaluate. Voting on patterns that were never loaded would be noise.
