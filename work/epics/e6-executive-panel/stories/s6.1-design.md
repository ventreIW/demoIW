# S6.1 Design — KPI Aggregation (Backend)

**Epic:** E6 · **Size:** S · **Complexity:** moderate (3 components, 0 external integrations, custom bucketing logic)
**Branch:** `story/s6.1/kpi-aggregation-backend`
**Governed by:** [ADR-009](../../../../dev/decisions/adr-009-kpi-reads-persisted-scores.md)

---

## Problem

The director has no portfolio view. Everything E4 computes is exposed one row at a time through
`/prioritized`, which is a work queue built for a collector — 271 rows ordered for triage, with no
statement of what the book is worth or where its value concentrates.

## Value

One endpoint that answers RF-06.1 and RF-06.2 from persisted data, cheap enough to call per request.
It is the hub of E6: s6.2 renders it and s6.3 executes NL intents against it (ADR-008), which is
what makes the dashboard and the NL answer structurally incapable of disagreeing.

## Gemba findings

Read: `prioritized_case.py`, `prioritizer.py`, `feature_extractor.py`, `case_aggregate_service.py`,
`routers/scenarios.py`, `routers/cases.py`, `container.py`, `main.py`, `ports/repositories.py`,
`adapters/persistence/sqlalchemy_scenario_repo.py`, `domain/exceptions.py`, `tests/`.

**S1 — `get_raw_dataset()` already returns exactly the frame this story needs.**
`IScenarioRepository.get_raw_dataset()` yields a `RawDataset` of three DataFrames with every column
required: `invoices.{client_id, amount, status, days_overdue, id}`, `payments.{invoice_id, amount,
paid_date}`. This changes the shape of the story — see D1.

**S2 — the "expected recoverable" formula exists once, as a property.**
`PrioritizedCase.expected_recoverable` is `outstanding * score / 100`, documented as *money, pesos*
because s4.3 kept `predict_proba` calibrated. It is currently unreachable without constructing a
`PrioritizedCase`, which requires a `rank` and a `client_name` this story has no use for. → D2.

**S3 — `categorize()` must not be re-run.** Persisted `Score.category` is already a `ScoreCategory`.
Recategorising from `score_value` would create a second banding that drifts if `LOW_THRESHOLD` /
`HIGH_THRESHOLD` ever change. Read the stored member.

**S4 — the s5.2 integration test only covers 404s.** `test_case_detail_endpoint.py` says so in its
own docstring: the data-composition path is unit-tested but never integration-tested, because
seeding needed the generate endpoint and that needs OpenRouter. E5's retro filed the fix as PAT-R-10
(seed via SQLAlchemy insert). This story is the first chance to apply it. → Testing strategy.

**S5 — `payments_df` has no columns at all when there are no payments.** `pd.DataFrame([])`, not an
empty frame with a schema. Any code touching `payments["invoice_id"]` unguarded raises `KeyError`.
`outstanding_by_client` already guards with `payments.empty`; `collected_to_date` must too.

**Legacy sweep.** Net-new, with one exception: D2 extracts an existing property's body into a
module-level function. There is exactly one call site (`PrioritizedCase.expected_recoverable`), it is
updated in the same commit to delegate, and no V1 is orphaned. No other module is superseded — the
KPI service sits beside `case_aggregate_service`, it does not replace it.

**Drift risk.** `governance/drift-hotspots.json` absent — rank check skipped. AG2 (clone
amplification) is the live risk for this story and is what D1/D2 exist to prevent: two definitions
of "what is owed" or "what we expect to recover" would both look plausible and drift silently. AG4
(fan-out >3 modules) does not apply — three files, one new router.

**Supply chain.** No new dependencies. pandas, FastAPI and Pydantic are already in use.

## Approach

A module-level async function composing **two** repository ports into a frozen aggregate, mirroring
`case_aggregate_service.fetch_case_aggregate()` so both a router and (in s6.3) a use case can call it.

### Design decisions

**D1 — Read DataFrames via `get_raw_dataset()`, not entities via five repos.**
The epic design sketched a five-repo composition. Gemba S1 makes that wrong: `outstanding_by_client()`
— the function ADR-009 requires this story to reuse — takes DataFrames. Going through the entity
repos would mean either converting back to DataFrames or writing a second balance calculation over
entity lists, which is precisely the duplication ADR-009 forbids. Two ports, not five:
`IScenarioRepository` (`get_by_id`, `get_raw_dataset`) and `IScoreRepository` (`get_by_scenario`).

**D2 — Extract `expected_recoverable(outstanding, score)` to a module-level function.**
In `prioritized_case.py`, beside `categorize()`. `PrioritizedCase.expected_recoverable` delegates to
it; the KPI service calls it directly. Three lines, one call site swept. Without this, the KPI
service inlines `outstanding * score / 100` and the queue's money and the dashboard's money become
two expressions that merely happen to agree today.

**D3 — All monetary figures cover scored clients only; unscored clients are counted, not hidden.**
E4 excludes clients with nothing outstanding from scoring (32–43% on this generator). Mixing an
all-clients denominator with a scored-clients numerator would make `recovery_rate_expected` quietly
wrong. So every figure is over scored clients, and the response carries `unscored_client_count`
alongside `client_count`. A director who sees "271 scored, 118 unscored" can judge coverage; one who
sees only "271" cannot tell whether the book is fully assessed.

**D4 — `PortfolioNotScoredError` in `domain/exceptions.py`; the router maps it to 409.**
The refusal has to live in the service, not the router, because s6.3's executor is the second caller
and must be refused identically. Returning zeros is the failure ADR-009 names: a $0 expected
recoverable is a legitimate answer for a settled book and an illegitimate one for an unscored book,
and zeros make them indistinguishable.

**D5 — `amount_range` buckets are per-scenario quartile boundaries, labelled in pesos.**
Fixed peso bands cannot work: invoice amounts are a generator parameter. Quartiles are self-
describing to a director ("the top quarter of accounts by balance") and always sum. Assignment is by
boundary comparison against `numpy.percentile`, not `pd.qcut` — `qcut` raises on duplicate edges,
which a portfolio with many equal or zero balances produces. When boundaries collapse, clients pile
into fewer buckets and the counts still sum; that is a degenerate portfolio reported honestly, not
an error.

**D6 — Totality over the bucket space.** Every dimension's `assign` is total: every scored client
lands in exactly one bucket of every dimension. The lowest `days_overdue_bucket` starts at **0**, not
1, because a scored client with no open invoices has a max days overdue of 0 and a `1-30` floor would
drop it. Asserted directly: per-dimension counts sum to `client_count`.

This is the story's central defect species, seen three times in this codebase now — s5.1's
`days_overdue` filter, the still-live `?category=High`, and both hidden by tests that iterated an
empty list. A sum assertion cannot pass vacuously.

### Components

| File | Change | Purpose |
|---|---|---|
| `app/domain/value_objects/portfolio_kpis.py` | create | `PortfolioKpis`, `SegmentBucket`, bucket assignment functions |
| `app/domain/value_objects/prioritized_case.py` | modify | extract `expected_recoverable()` (D2) |
| `app/domain/exceptions.py` | modify | add `PortfolioNotScoredError` (D4) |
| `app/application/services/kpi_aggregate_service.py` | create | `fetch_portfolio_kpis()` — composes the two ports |
| `app/routers/executive.py` | create | `GET /{id}/kpis`, response models, 404/409 mapping |
| `app/main.py` | modify | register the router |
| `backend/tests/unit/test_portfolio_kpis.py` | create | bucketing + aggregate arithmetic |
| `backend/tests/unit/test_kpi_aggregate_service.py` | create | service over stub ports |
| `backend/tests/integration/test_kpi_endpoint.py` | create | seeded via SQLAlchemy (PAT-R-10), not the generate endpoint |

**Lean gates.** *KISS* — one function, two ports, no caching, no persistence. *DRY* — D1/D2 exist
solely to avoid a second definition of owed and recoverable. *YAGNI* — no trend metrics (no
historical snapshots exist), no cache (ADR-009 §Alternatives). *MVP* — three dimensions is the
minimum satisfying "≥2" with room for one to be cut if the story exceeds S.

### The three-client worked example

Fixture from `s6.1-story.md` §Examples. A=10,000 open with 4,000 paid, score 80; B=20,000 open,
score 40; C=5,000 settled, score 90.

```python
kpis.total_outstanding          == 26_000.0    # (10_000 - 4_000) + 20_000 + 0
kpis.total_expected_recoverable == 12_800.0    # 6_000*.80 + 20_000*.40 + 0*.90
kpis.collected_to_date          ==  5_000.0    # only C's settled invoice
kpis.recovery_rate_actual       == pytest.approx(0.16129, rel=1e-4)
kpis.recovery_rate_expected     == pytest.approx(0.49231, rel=1e-4)
kpis.cases_by_category          == {ScoreCategory.HIGH: 2, ScoreCategory.MEDIUM: 0, ScoreCategory.LOW: 1}
```

A is the load-bearing row: 4,000 is paid but its invoice is still open, so the money is neither
outstanding nor collected. An implementation that adds it to `collected_to_date` inflates the
recovery rate; one that ignores the partial payment overstates exposure by 4,000.

### Signatures

```python
# app/domain/value_objects/prioritized_case.py
def expected_recoverable(outstanding: float, score: float) -> float: ...

# app/domain/value_objects/portfolio_kpis.py
@dataclass(frozen=True)
class SegmentBucket:
    label: str
    client_count: int
    outstanding: float
    expected_recoverable: float

@dataclass(frozen=True)
class PortfolioKpis:
    scenario_id: UUID
    scenario_name: str
    sector: Sector
    scored_at: datetime
    client_count: int
    unscored_client_count: int
    total_outstanding: float
    total_expected_recoverable: float
    collected_to_date: float
    cases_by_category: dict[ScoreCategory, int]
    segmentation: dict[str, list[SegmentBucket]]

    @property
    def recovery_rate_actual(self) -> float: ...      # 0.0 when nothing collected and nothing owed
    @property
    def recovery_rate_expected(self) -> float: ...    # 0.0 when total_outstanding == 0

# app/application/services/kpi_aggregate_service.py
async def fetch_portfolio_kpis(
    scenario_id: UUID,
    scenario_repo: IScenarioRepository,
    score_repo: IScoreRepository,
) -> PortfolioKpis: ...
    # raises EntityNotFoundError  -> 404
    # raises PortfolioNotScoredError -> 409
```

Both rates are derived properties for the same reason `expected_recoverable` is: a stored ratio can
drift from the figures it was computed from.

## Acceptance criteria

Gherkin scenarios live in `s6.1-story.md`. Refinements:

**MUST**
1. Every figure and dimension in the 200 example is present and correctly typed (story AC 1–2).
2. Unscored scenario → 409 naming `POST /score`; unknown scenario → 404 (story AC 3–4).
3. `total_outstanding` is produced by `feature_extractor.outstanding_by_client()`; the partial-payer
   case asserts 6,000, not 10,000 and not 2,000 (story AC 5).
4. `cases_by_category` carries every `ScoreCategory` member including zero counts, read from
   `Score.category` (story AC 6).
5. Per-dimension bucket counts sum to `client_count` for all three dimensions.
6. `unscored_client_count` is reported (D3).

**SHOULD**
7. `scored_at` is the max `Score.scored_at` of the persisted run, so s6.2 can show staleness.
8. Response models carry docstrings naming the formula, as `PrioritizedCase` does.

**MUST NOT**
9. No model is fitted in the request path — no import of `ScoreScenario`, `SklearnScorer` or
   `FeatureExtractor.extract` from the service or router. Asserted structurally, as an executable
   test rather than a checklist line (four stories of evidence that checklist ACs do not hold).
10. No second definition of outstanding balance or expected recoverable value.
11. No client silently dropped by a bucket boundary — covered by AC 5, which cannot pass vacuously.

## Testing strategy

| Layer | Test | Purpose |
|---|---|---|
| unit | `test_portfolio_kpis.py` — worked example above | Arithmetic against hand-computed figures, including the partial payer |
| unit | bucket assignment totality | Every client lands in exactly one bucket of every dimension; counts sum |
| unit | degenerate portfolios | All-equal balances (collapsed quartiles), all-zero outstanding, single client |
| unit | `test_kpi_aggregate_service.py` over stub ports | `EntityNotFoundError` on unknown scenario, `PortfolioNotScoredError` on empty scores, no-payments case (gemba S5) |
| integration | `test_kpi_endpoint.py` | 200 / 404 / 409 by status **and** body. **Seeded with direct SQLAlchemy inserts** (PAT-R-10) so the composition path is genuinely integration-tested — the gap s5.2's own docstring admits — and no test spends OpenRouter quota |
| structural | no-model-fit import assertion | AC 9 |

Manual verification closes the story: `curl` the endpoint against the running app on a real scored
scenario, check the sums by hand, and **commit the captured payload** as the source s6.2 builds its
TypeScript type from. s5.1 shipped a defect through design, types, component and fixture because
every layer inherited one assumption read from the domain classes; `?category=High` is the same
species and is still live in this repo.
