# BUG-09: analysis

## Method: Two-source-of-truth comparison

The exception names the two types. The work is enumerating how far the divergence extends and
deciding which declaration is authoritative.

## Extent

| Table | PK in migration 0002 | PK in ORM |
|---|---|---|
| scenarios | `postgresql.UUID(as_uuid=False)` | `String(36)` |
| clients | `postgresql.UUID` | `String(36)` |
| invoices | `postgresql.UUID` | `String(36)` |
| payments | `postgresql.UUID` | `String(36)` |
| scores | `postgresql.UUID` | `String(36)` |
| communications | `postgresql.UUID` | `String(36)` |
| contact_results | `postgresql.UUID` | `String(36)` |

Plus every foreign key — 16 UUID columns in `0002` in total. The divergence is complete and
systematic, not a single missed column.

## Root cause

**Two independent declarations of one schema, with nothing forcing agreement, and a test
environment that could not expose the difference.**

The migrations were hand-written (they are not autogenerated from the models — `0002` creates
all seven tables in one revision with explicit `postgresql.UUID` types). The ORM was written
separately with `String(36)`, which is a perfectly reasonable way to hold a UUID as text.

Neither is wrong in isolation. What is wrong is that **no mechanism compared them**, and the
only environment that could have — PostgreSQL — is the one nothing ran against. On SQLite,
`create_all` builds the schema *from the ORM*, so the migrations are not merely unverified:
they are **not executed at all**. The two declarations never met.

This is the same shape as BUG-02 and BUG-03 — a value with two sources of truth that drift —
but at schema scale, and with a far larger blast radius, because the divergence disables all
persistence rather than one filter.

## Why M4 was the only thing that could have found it

Every other gate passes:

- 563 tests pass — they run on SQLite.
- `mypy` passes — both declarations are well-typed Python.
- `ruff` passes — no style issue.
- CI passes — it runs the same SQLite suite.
- `alembic upgrade head` succeeds — creating a schema is not the same as writing to it.

The failure requires the ORM and the migration-built schema to meet, which happens only when
the application writes to a database that Alembic created. That is precisely and exclusively
what E6's M4 line item specifies, and it is the item that was deferred across E4, E5, s6.2,
s6.3, s6.4 and E7.

**E6's scope justified M4 on the grounds that "E4's M4 caught a generation-layer bug no unit
test saw, and E5's M4 repeated the lesson."** This is the third instance and the most severe:
the first two found bugs in features; this one found that the product does not work.

## Which declaration is authoritative

The migrations. `postgresql.UUID` is the correct column type for a UUID in PostgreSQL —
16 bytes rather than 36, validated by the database, and correctly indexed. The ORM's
`String(36)` is the accommodation, made so the same models could run on SQLite in tests.

The fix therefore changes the ORM to a type that is **native `uuid` on PostgreSQL and text on
SQLite**: SQLAlchemy 2.0's `sa.Uuid(as_uuid=False)`, which is the portable spelling of exactly
what the migrations already declare. `as_uuid=False` preserves the current Python-side contract
— the ORM continues to hold `str`, mappers continue to call `UUID(orm.id)` and `str(domain.id)`
— so no application code changes.

Changing the migrations to `VARCHAR(36)` would also make the two agree and would be a smaller
diff, but it would bend the database to the test environment's limitation, which is the wrong
direction.

## Fix approach

Replace `String(36)` with `Uuid(as_uuid=False)` on all seven primary keys, and let the foreign
keys inherit the referenced column's type. Run the suite on SQLite **and** on PostgreSQL — the
second is now possible, and is the only way to know the fix works.
